run07_filtered.py 代码逻辑 —— 用 dcu_probe 的 pt_compare 复核 verl 0.7 训推一致性

这个脚本本身不算精度 —— 它做的是「把训练侧、推理侧的 dump 配对好、过滤干净,再交给 dcu_probe 的官方比对工具 pt_compare 去逐算子算误差」。

真正发挥效果的 dcu_probe 工具 = pt_compare;脚本的 5 步里,前 3 步都是在「为 pt_compare 准备能对齐的输入」,第 4 步才调 pt_compare,第 5 步读它的结果。

★ 核心工具:dcu_probe 的 pt_compare(官方精度比对 API)

pt_compare 是什么、发挥什么效果

来自 dcu_probe.pytorch.compare.pt_compare(= 华为 msprobe compare 的 DCU fork)。它是 dcu_probe 提供的官方逐算子精度比对能力,本脚本调的就是它:

# 训练侧 dump ↔ 推理侧 dump,逐算子比对 pt_compare({"npu_path": 训练侧dump.json, "bench_path": 推理侧dump.json}, output_path, consistent_check=True, backend="fsdp")

它内部干这几件事(效果):

  • 读两侧 dump.json → 建两张算子表(NPU=训练侧、Bench=推理侧)。
  • consistent_check=True → 走 verl 训推一致专用比对算法(而非普通逐 tensor 比)。
  • backend="fsdp" → 用 FSDP_MODULE_MAP 把 HF 命名映射到 vllm 命名(q/k/v_proj → qkv_proj、gate/up → gate_up)。
  • consistent_match → dual_monotonic_sort → 把两侧算子按位置单调对齐(⚠️ 这一步要求两侧算子位置能同时单调递增,0.7 直接喂会在这崩)。
  • 逐算子算 NormRelativeErr(Norm 相对误差)→ 落 compare_result_*.xlsx。

关键:脚本要做的就是"喂给 pt_compare 一份两侧能单调对齐的输入" —— 而 0.7 的 das vllm 0.18.1 dump 里有 72 个训练侧没有的交错模块,会破坏对齐 → 所以脚本第 3 步先把它们过滤掉,pt_compare 才跑得通。

① 按 request_id 配对两侧 dump → ② 挑同 prompt 完整 prefill 样本 → ③ 过滤 bench-only 交错模块(338→266) → ④ 调 pt_compare → ⑤ 读 xlsx 排除+统计(98/98 <1%)

配对

把两侧对上号

pt_compare 一次只比一对 dump.json(一个训练前向 vs 一个推理前向)。这步用 request_id 把两侧对上:推理侧从 dispatch_log 找、训练侧从 update_actor_log 找。

只取单 request(推理 requests==1 / 训练 num_requests==1)的 prefill —— 多 request 拼 batch 的 dump 是混合张量,无法逐层比。das 会给 id 加 -<8hex> 后缀,strip 去掉才对得齐。

②挑同 prompt 的完整 prefill 样本保证 pt_compare 比的是同一个东西
common = set(gen) & set(train) # 两侧都有的 request_id
good = [rid for rid in common
if tok(train[rid],["embed_tokens"]) == tok(gen[rid],["embed_tokens"])]
rid = good[0] # 选一个两侧 embed 输入 token 数完全相同的
tp = train[rid]; gp = gen[rid]
对齐

token 数一致 = 真·同 prompt

tok() 取 embed_tokens 的输入 token 数。两侧相同,才说明喂进模型的是同一个 prompt 的完整 prefill(没被 prefix cache 截断、没被 batch 拼)。

选一个这样的 rid,拿它的训练 dump(tp)和推理 dump(gp)去比 —— 这就是要喂给 pt_compare 的那一对。

③★过滤 bench-only 交错模块(run07_filtered 的灵魂)让 pt_compare 的 dual_monotonic_sort 不崩
DROP = re.compile(r"Triton\.|rotary_emb|reshape_and_cache|unified_attention")

关键

剔掉训练侧没有的 72 个交错模块

0.7 用 das vllm 0.18.1,推理 dump 里比训练侧多出 72 个训练侧无对应、且位置交错的模块:Triton.kernel_unified_attention×24 + reshape_and_cache×24 + 独立 rotary_emb×24。

不剔它们 → pt_compare 的 dual_monotonic_sort 因两侧位置无法同时单调递增而 raise Conflicting comparison data(run_fsdp_compare_07.py 就崩在这)。剔掉后 338→266,两侧就能对齐。

这些模块本就不是"可比叶子算子"(训练侧根本没有),剔除是方法学正当的。

dcu_probe 工具

官方逐算子比对就在这一行

前 3 步全是铺垫,这一行才是真正发挥效果的 dcu_probe 工具。它读两侧 dump.json,用 consistent_check+backend=fsdp 的专用算法把算子对齐(FSDP_MODULE_MAP 命名映射 + dual_monotonic_sort 单调对齐),逐算子算 Norm 相对误差,落 xlsx。

脚本 vs 工具的分工:脚本负责"喂对齐好的数据",pt_compare 负责"算误差、出报告"。

⑤读 xlsx,排除+统计把 pt_compare 的结果整理成结论
df = pd.read_excel(xlsx) # pt_compare 出的报告
m = df[NPU与Bench都非空] # 双边 match 的行
EXCLUDE = "Qwen2DecoderLayer|Qwen2MLP|Qwen2Attention|IdentityOp|act_fn|SiLU"
real = m[is_output & ~is_excluded] # 只留真叶子算子
print("<1%: %d/%d" % ((real.nerr < 1).sum(), len(real))) # 98/98
统计

排除结构性不可比,报叶子算子分布

pt_compare 会把所有算子都列进 xlsx,包括结构性不可比的:整层 wrapper(输出是残差和)、IdentityOp、act_fn 融合算子(HF silu(gate) vs vllm SiluAndMul)。这步用正则排除它们,只统计真叶子算子(o_proj/down_proj/layernorm/embed/norm)。

结果:可比叶子算子 98 个,<1%: 98/98(中位 0.15%、max 0.61% o_proj)。

pt_compare vs verify_consistency.py vs run_fsdp_compare_07.py 的区别

关键区分:pt_compare 是 dcu_probe 的官方比对工具(底层能力);三个脚本的差别在于「用不用它、怎么喂它」。

对象是什么用 pt_compare?在 0.7 上粒度 / 结果
pt_comparedcu_probe 官方比对 API(底层工具,华为 msprobe compare 的 DCU fork)—(它本身就是工具)直接喂 0.7 dump 会崩逐算子 NormRelativeErr,出 xlsx
verify_consistency.py自研外挂脚本(原来 0.7 收官用的)❌ 不用 —— 自己读 dump.json 比✅ 可用(绕开 pt_compare 的盲区)只比 embed + 每层 2 layernorm 的 normed 输出 → 80/80 <1%
run_fsdp_compare_07.py调 pt_compare 原版(0.8 那套,不过滤)✅ 用❌ 崩(dual_monotonic_sort)—(72 交错模块撑爆对齐)
run07_filtered.py= run_fsdp_compare + 先过滤交错模块✅ 用✅ 通叶子算子 98 个 → 98/98 <1%

① verify_consistency.py(自研,不碰 pt_compare)
当年 0.7 收官就是它。完全不调 pt_compare —— 自己读两侧 dump.json,只比"两侧语义严格对应的 normed 算子"(embed + 每层 input_layernorm/post_attention_layernorm 的 Norm),主动绕开 das 的 fused residual 假 diff 和 dual_monotonic_sort 崩点。优点:简单、稳、在 0.7 上直接能跑;代价:粒度粗(只 80 个 normed 算子,不覆盖 o_proj/down_proj),且是"自研口径"非官方工具。

② run_fsdp_compare_07.py(调 pt_compare 原版,不过滤)
这是 0.8 后端那套官方 compare,直接把配对好的两侧 dump 喂 pt_compare(consistent_check=True, backend="fsdp")。在 0.8(das vllm 0.11)dump 上能过(模块序干净);但在 0.7(das vllm 0.18.1)dump 上崩在 dual_monotonic_sort —— 因为多了 72 个交错模块。

③ run07_filtered.py(= ② + 过滤)
只比 run_fsdp_compare_07.py 多一步 ③ 过滤(剔掉那 72 个 bench-only 交错模块 338→266),就让同一个 pt_compare 在 0.7 上也跑通了。用的是官方工具口径,覆盖更全(98 个叶子算子,含 o_proj/down_proj),结果 98/98 <1%,与自研 80/80 相互印证。

一句话记住三者关系:
pt_compare = dcu_probe 官方比对工具(核心能力) verify_consistency.py = 绕开 pt_compare,自研只比 normed 算子(80/80,原来用的) run_fsdp_compare_07.py = 直接喂 pt_compare,0.7 上崩(证明官方工具不能裸用) run07_filtered.py = 过滤后喂 pt_compare,0.7 上通(98/98,官方口径复核)
