原生 PyTorch 接入 dcu_probe —— 4 坑 + 验证三件套 + L0/L1 覆盖

pytorch 是最直接的接入:直接在你的 train loop 里调 _common.lifecycle 的 5 个 hook —— 无 Feature(dcu_megatron)、无 callback、无源码 patch(verl)。所以这里的坑不在框架胶水,而在 whl 依赖 与 产物验证。

验证场景 = 精度对比 / 采集验证(单侧 dump + monitor 三通道),不是训推一致,没有 pt_compare。本页把 4 个坑各拆一张卡,再给验证三件套 + L0/L1 覆盖差异 + 诚实实测状态。

4 坑速览 —— 都不是框架问题,是「依赖 / 权限 / 采集语义」问题

pytorch 接入本体只有几行 lifecycle hook,采集起不来时先按这 4 类排查:前 3 类所有框架通用,第 4 类是 pytorch 特有(优化器你自己选,采不采得到 optimizer 通道取决于它有没有 state)。

最迷惑

「loss 正常」骗过所有人

lifecycle 的 dump / monitor 子系统都硬依赖 tensorboard。缺它时 PrecisionDebugger / TrainerMonitorV2 的 init 会静默失败,但你的训练循环照跑、loss 照打印 —— 完全看不出采集没起来。

这就是为什么「只看 loss 正常 ≠ 采集成功」。判据只能是产物:有没有 dump.json、有没有三通道 csv。见下方「验证三件套」。

⚠ 2output_dir / dump_path 相对 cwd + 产物 0o750 权限产物落哪 + host 读不读得到
# cfg 里的 dump_path / output_dir 是「相对进程 cwd」的相对路径
loss_output_dir = resolve_loss_output_dir(
dump_cfg_path=args.dump_cfg,
monitor_cfg_path=args.monitor_cfg,
)
# → 先搞清楚从哪个目录起进程,产物到底落在哪
# 容器 root 建的产物默认 0o750,host 侧读不到:
$ docker exec <ctr> chmod -R 755 <dump_path> <output_dir>
路径 / 权限

相对路径 + root 权限双坑

dump 的 dump_path 和 monitor 的 output_dir 都是相对进程 cwd 的相对路径。resolve_loss_output_dir()(verbatim)会据两份 cfg 定 LossTracker 落点 —— 但你得先确认从哪个目录启动,否则产物落到意料外的地方,看起来像「没产出」。

容器里 root 建的 dump.json / csv 是 0o750,host 侧非 root 用户读不到 → 容器内 chmod -R 755(或 docker exec cat 直接看)。

⚠ 3monitor 三通道约束 —— patch_optimizer_step=false + 不开 module同所有框架的 monitor 约束
// monitor_v2_config_resnet.json
{
"monitors": {
"weight_grad": { ... }, // 通道①
"optimizer": { "mv_distribution": true }, // 通道②
"param": { ... } // 通道③
},
"ops": ["min","max","mean","norm","nans"],
"patch_optimizer_step": false, // ← 由循环手动 on_step_end 驱动 step
// 不开 monitors.module 通道(易抓到 wrapper,非叶子)
}
采集语义

三通道 + 手动驱动 step

monitor 三通道 = weight_grad / optimizer(mv_distribution) / param。两条硬约束(和 megatron / verl 一致):

① patch_optimizer_step:false —— 你的 train loop 里已经手动在每 step 调 mon_lc.on_step_end(...) 驱动 monitor 前进,不需要它再去 monkey-patch optimizer.step,否则会重复推进。

② 不开 monitors.module 通道 —— module 通道容易抓到 Sequential / wrapper 这类非叶子结构,三通道够用。

⚠ 4optimizer 通道需 Adam 这类有 state 的优化器★ pytorch 特有:优化器你自己选
model_ctor = getattr(models, args.model)
model = model_ctor(weights=None).to(device)
optimizer = optim.Adam(model.parameters(), lr=args.lr)
criterion = nn.CrossEntropyLoss()
# Adam 有 exp_avg / exp_avg_sq state,
# monitor.optimizer.mv_distribution 才能采到东西
# 换 optim.SGD(无动量)→ optimizer 通道采空
# —— 不是 bug,是优化器本身没 state
pytorch 特有

optimizer 通道采的是优化器 state

其它框架优化器是框架定死的;pytorch 里优化器是你自己 optim.Adam(...) 建的,所以这条要特别强调。

monitor 的 optimizer 通道采的是 mv_distribution = Adam 的一阶/二阶动量(exp_avg / exp_avg_sq)。用 SGD(无 momentum)这类没有 per-param state 的优化器,这个通道采不到任何东西 —— 目录里 optimizer_*.csv 空,但这不是采集失败,是优化器本身没 state。样例固定用 Adam。

验证三件套 —— 中看 marker、后查产物、再核权限

纪律:绝不凭「loss 正常 / exit 0 / 无报错」判采集通过(坑 1 就是反例)。采集是否真起来,只认下面这三件。

验证链路:
中:看 marker → 后:查产物存在 + 数量 → 再核权限 chmod 755
中grep stdout 看 init marker(不是看 loss)坑 1 静默失败靠这一步暴露
$ python train_resnet_dcu_probe.py --dump-cfg L0.json --monitor-cfg monitor.json 2>&1 | grep -E "initialized|started"
PrecisionDebugger initialized with L0.json # dump 起来了
TrainerMonitorV2 initialized and started # monitor 起来了
# 两条都没有 → 采集没起(多半是坑 1 tensorboard 缺失)
中

marker 是「起没起来」的第一信号

init 成功会各打一条 marker:dump 侧 PrecisionDebugger initialized with <cfg>、monitor 侧 TrainerMonitorV2 initialized and started。看 loss 打印没用(loss 走的是训练循环,与采集无关);要 grep 这两条。

⚠️ ray / 多进程场景下 worker 的 marker 可能传不回主 stdout,所以 marker 只是第一信号,最终判据仍是产物。

后查三类产物存在 + 数量对文件存在 ≠ 内容有效,还要数量对
# ResNet50 单卡 · both 模式(--dump-cfg + --monitor-cfg)· --steps 5
$ find <output_dir> <dump_path> -name "*.csv" -o -name "dump.json"
<output_dir>/rank_0/weight_grad_*.csv # 三通道 csv
<output_dir>/rank_0/optimizer_*.csv # (单卡 → 只 rank_0)
<output_dir>/rank_0/param_*.csv
<dump_path>/step0/dump.json step1/… step2/… # 按 cfg 的 step 列表
<output_dir>/loss_log.csv # LossTracker,行数 = step 数
后

三类产物、逐类对数量

both 模式应同时落这三类:

① monitor csv:单卡 → rank_0/ 下 weight_grad / optimizer / param 三通道各有 csv(optimizer 通道非空 = 坑 4 的 Adam 生效);
② dump.json:按 dump cfg 的 step 列表(如 [0,1,2])各一份,打开看 module 数 / shape / 有没有 NaN,别只看文件在;
③ loss_log.csv:LossTracker 单例产物,行数 = step 数。

再核权限(坑 2 收尾): 产物是容器 root 建的 0o750,host 侧读不到就以为「没产出」。验证前先 docker exec <ctr> chmod -R 755 <dump_path> <output_dir>,或干脆 docker exec cat 在容器里看。「数量对」也不等于「内容有效」 —— dump.json 要打开看 module 数 / 统计值 / NaN,csv 要看真有数值行。

L0 vs L1 覆盖 —— 只改 cfg 的 level 字段,脚本一行不动

dump 的粒度由 dump cfg 的 level 字段切换。lifecycle 的 hook(on_step_start(model=model) 挂 module 遍历)对 L0 / L1 是同一套,换粒度不改代码,只改 JSON。

层级cfg 字段粒度抓什么产物量 / 场景
L0 "level": "L0" module 级 每个 nn.Module 的 forward 输入 / 输出统计(min/max/mean/norm/nan) 量小、module 名索引清晰,生产 / 精度对比推荐(样例实测跑的就是 L0)
L1 "level": "L1" API 级 每个 torch / Tensor / Functional API 调用的统计(算子数量大得多、更细) 量大,适合单侧深剖某段精度;L1 未逐项实测
换粒度 = 改一个字段:
dump_config_resnet_L0.json {… "level": "L0" …} → 改成 "level": "L1" → 同一条 --dump-cfg 跑,脚本 / hook 不动

诚实实测状态 —— 采得到 ≠ 训得好,别外推

✅ 已实测(ResNet50 / Adam / 单卡 / 随机数据 / 5 step)
dump(L0)+ monitor 三通道(weight_grad / optimizer / param)+ LossTracker 均实跑落盘:三类产物都产出、optimizer 通道因用 Adam 非空、loss_log.csv 行数对上 step 数。

⚠️ 但这只证「hook 挂得上 + 产物写得出」,不证收敛
样例用随机数据(torch.randn 输入 + randint 标签),5 step loss 会快速过拟合到一个假的小值 —— 这是 PoC 特性,不代表训练健康。要验训练健康得换真实数据 + 看几十步 grad_norm / loss 趋势(接入铁律:先验 baseline 训练健康,再谈采集)。

◻ 未逐项实测
L1(API 级)、多卡、其它模型 / 优化器 走的是同一套 _common.lifecycle 机制,预期可用,但未逐项实跑 —— 需要时按本页 4 坑 + 验证三件套逐条核。
