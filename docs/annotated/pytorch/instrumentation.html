hcu_probe × 原生 PyTorch —— 接入标注（5-hook lifecycle 直接织入，最简）

原生 PyTorch / 任意自定义 train loop（样例 = ResNet50 + Adam，单卡）接 hcu_probe 做精度对比 / 采集验证——dump 采每 step 前向逐 module 统计量、monitor 采 weight_grad / optimizer / param 三通道。这是单侧训练态数据，供离线精度分析。不是训推一致（那是 verl 双侧配对）。

本页标注在你自己的训练脚本里织入 5 个 lifecycle hook 的 6 处位置。左侧是 verbatim ResNet 训练代码（绿色高亮 = 你新增的 hcu_probe 行），右侧是说明。这是最直接的接入——无 Feature（hcu_megatron）、无 callback（transformers）、无源码 patch（verl），直接 import _common.lifecycle 按训练阶段调 hook，几行即可。不传 cfg = 原训练、零影响（最小侵入）。

总览：1 个文件、5 个 lifecycle hook、0 行 patch

改动只在你自己的训练脚本里（train_resnet_hcu_probe.py），不碰任何框架本体、不注册任何东西。全部由两个 argparse flag --dump-cfg / --monitor-cfg 门控——都不传就是普通 ResNet 训练。

#调用训练循环阶段作用门控
①dump_lc.on_train_start(...)初始化后（model / optimizer 建好）构造 PrecisionDebugger + 固定 seed + 挂 LossTracker--dump-cfg
②mon_lc.on_setup_done(...)初始化后（拿 model + optimizer）构造 TrainerMonitorV2，挂三通道监控--monitor-cfg
③dump_lc.on_step_start(model=model)每 step forward 前debugger.start(model) 注册前向钩子--dump-cfg
④dump_lc.on_step_end(...)每 step 算完 loss / grad 后stop()+step() → 落 dump.json + loss_log--dump-cfg
⑤mon_lc.on_step_end(...)同上位置（紧跟 ④）monitor.step() → 三通道 csv--monitor-cfg
⑥on_train_end() ×2训练结束flush / close（monitor 先、dump 后）各自 cfg
为什么说这是"最直接的接入" —— 对比另两个框架：verl 要改 3 仓源码、在 forward 处插钩子 patch；hcu_megatron 要注册 Feature 类、运行时 monkey-patch。而原生 PyTorch → 在你已有的 train loop 里 import 一行、按阶段调 5 个 hook，没有 Feature、没有 callback、没有源码 patch、没有注册表。_common.lifecycle 是框架无关的地基 API——hcu_megatron 的 Feature、verl 的 patch 兜兜转转最终都调进它，pytorch 只是直接调地基、跳过中间胶水。最小侵入 不传 cfg 时全部 if args.*_cfg: 为假，一行 hcu_probe 都不进 = 原训练。

核心 API：两个单例 + 一个路径解析（全在 whl 里）

整个接入只 import 三个符号：两个 get_*_lifecycle() 返回进程内单例（dump 与 monitor 各一个，不用自己 new），resolve_loss_output_dir 从 cfg 推出统一的 LossTracker 落点。之后所有 hook 都是 dump_lc. / mon_lc. 的方法调用。

from hcu_probe.integrations._common.lifecycle import get_dump_lifecycle, get_monitor_lifecycle
from hcu_probe.integrations._common.config import resolve_loss_output_dir
dump_lc = get_dump_lifecycle() # 进程内单例（dump 子系统）
mon_lc = get_monitor_lifecycle() # 进程内单例（monitor 子系统）
loss_output_dir = resolve_loss_output_dir(dump_cfg_path=..., monitor_cfg_path=...)

业务逻辑全在 whl 里：PrecisionDebugger / TrainerMonitorV2 的构造、rank 过滤、cfg 解析、LossTracker 去重，都封在 lifecycle 单例内部。脚本只负责"在对的训练阶段调对的 hook"。resolve_loss_output_dir 让 both 模式共用一份 loss_log.csv（LossTracker 单例去重，loss 只记一份）。

核心 · monitor
monitor 监控 · 起点

monitor 挂 model + optimizer

on_setup_done 拿 model + optimizer 构造 TrainerMonitorV2，挂 weight_grad / optimizer / param 三通道。名字"setup_done"= 模型 / 优化器都建好后调（与 dump 的 on_train_start 位置相同、语义强调"setup 完成"）。

必须传 optimizer：optimizer 通道采 mv_distribution（Adam 的 exp_avg / exp_avg_sq 一阶二阶动量），没有 optimizer 这通道采不到东西。grad_acc_steps=1 告诉 monitor 几个 micro-step 算一个真 step。

dump 采集 · 逐 step

必须在 forward 之前调

on_step_start(model=model) 在这一步 forward 之前调 debugger.start(model)，给每个 module 注册前向 hook 抓这一步的逐 module 统计量。

位置关键：必须在 out = model(fake_input) 之前，否则这步 forward 抓不到。

monitor 没有 on_step_start——它按 optimizer step 采权重/梯度/动量，不需要前向钩子，所以这一处只有 dump 一个 hook。

停采 + 落 dump.json

算完 loss / grad 后 on_step_end(step, loss_dict, grad_norm) 内部调 debugger.stop() + step() → 落 step{N}/dump.json，同时 LossTracker 把 loss / grad_norm 记进 loss_log.csv。

核心 · monitor
monitor 监控 · 落盘

同一位置、第二个 hook

monitor 的 on_step_end 紧跟 dump 的那行，同一 step 位置两个子系统各调一次。这次 monitor.step() 采 weight_grad / optimizer / param 三通道写 csv。

为什么要手动调：cfg 里设 patch_optimizer_step=false，所以 monitor step 由循环里这行手动驱动（不 monkey-patch 你的 optimizer.step()）。

两个子系统独立、互不干扰；both 模式两 hook 都调，loss 由 LossTracker 单例去重只记一份。

# cleanup（顺序：monitor 先停 → dump 后停）
+ if args.monitor_cfg:
+ mon_lc.on_train_end()
+ if args.dump_cfg:
+ dump_lc.on_train_end()
收尾顺序
收尾 · dump + monitor

monitor 先停、dump 后停

收尾顺序固定：mon_lc.on_train_end() 先，dump_lc.on_train_end() 后。各自 flush / close 自己的 debugger 与 monitor writer。

LossTracker 不用手动 close——它在两者的 on_train_end 内部自动 close。both 模式两个都调，各自门控互不影响。

5 个 lifecycle hook 全表

同一套 lifecycle，dump 与 monitor 两条通道各按训练阶段调；只有 5 个 hook 名（on_step_end 在同一位置被两条通道各调一次，故 5 hook 落成 6 处）。

同一套 lifecycle 地基，三种织入方式

dump / monitor 的真正业务实现（PrecisionDebugger、TrainerMonitorV2、LossTracker、rank 过滤）都在 hcu_probe.integrations._common.lifecycle 这套框架无关地基里。三个框架只是把 hook 织进训练流程的方式不同，最终都汇到同一个地基。
