原生 PyTorch dcu_probe 采集模式 + argparse CLI —— dump / monitor

这一页讲「采什么、怎么开」:4 种采集模式(baseline / dump / monitor / both),全部由你训练脚本自己的 argparse 两个 flag --dump-cfg / --monitor-cfg 控制。

pytorch 是最直接的接入 —— 控制面就是你脚本里的 argparse:不传 flag = 原生训练一行不改,传了才启对应 lifecycle。单侧训练态精度采集,无 pt_compare、非训推一致(那是 verl 干的事)。

★ 控制面:你脚本自己的 argparse 两个 flag(比 megatron 简单)

--dump-cfg / --monitor-cfg 就是全部开关

采集完全由训练脚本 parse_args() 里加的两个参数控制,每个参数的值 = 一个 JSON cfg 路径。传谁启谁,都不传就是 baseline 原训练:

# baseline —— 一行 dcu_probe 都不跑 python train_resnet_dcu_probe.py # dump(L0 module 级 statistics) python train_resnet_dcu_probe.py --dump-cfg dump_config_resnet_L0.json # monitor(weight_grad/optimizer/param 三通道 csv) python train_resnet_dcu_probe.py --monitor-cfg monitor_v2_config_resnet.json # both —— dump + monitor 同一进程并存 python train_resnet_dcu_probe.py --dump-cfg L0.json --monitor-cfg monitor.json

为什么说它比 megatron 简单:

  • flag 名是你 argparse 自己起的(不是 dcu_probe 规定),想叫 --probe 也行 —— 它只是被你的代码用来选「传不传 cfg」。
  • 直接在你自己的 argparse 里:不用穿过 run.sh → pretrain → arguments 多层启动脚本,没有任何框架启动胶水。
  • 不做「下划线↔连字符」名字转换:megatron 的 flag 要在启动链里做 --dcu-probe-dump ↔ dcu_probe_dump 的转换才能落到参数;pytorch 直接 args.dump_cfg 拿到,零转换。
  • 启停机制就是一个 Python 判断:if args.dump_cfg: 为 False 就整段 lifecycle 都不执行 = 纯原生训练。

关键:这里没有 pt_compare、没有推理侧、没有配对 —— pytorch 只在训练一侧把每步的模块统计 / 三通道量落盘,供离线精度分析。要「训练 vs 推理逐层比」那是 verl 的场景,不在本页。

4 种采集模式矩阵

同一份训练脚本,靠传不传两个 cfg flag 切出 4 种采集模式:

模式flag采什么产物
baseline(不传)—(纯原生训练,dcu_probe 完全不介入)只有你自己的 stdout / ckpt
dump--dump-cfg dump_config_resnet_L0.jsonL0 module 级 statistics(改 level=L1 即 API 级)dump_path/step{0,1,2}/dump.json
monitor--monitor-cfg monitor_v2_config_resnet.json三通道 weight_grad / optimizer / paramoutput_dir/rank_0/{weight_grad,optimizer,param}_*.csv
both两个都给dump + 三通道 csv 同时采上面两套 + 共用一份 loss_log.csv
整条控制链路(从 flag 到落盘):
parse_args() 拿到 args.dump_cfg / args.monitor_cfg → resolve_loss_output_dir() 定 loss 落点 → if args.dump_cfg:启 dump lifecycle / if args.monitor_cfg:启 monitor lifecycle → 训练循环里 hook fire → 落 dump.json / *.csv
①baseline —— 不传 cfg = 原训练guard 为 False,dcu_probe 一行不跑
def parse_args():
p = argparse.ArgumentParser()
p.add_argument("--monitor-cfg", default=None, help="path to monitor v2 JSON")
p.add_argument("--dump-cfg", default=None, help="path to L0/L1 dump JSON")
...
# 训练脚本里的两处 guard:
if args.dump_cfg: # None → 整段 dump lifecycle 跳过
dump_lc.on_train_start(...)
if args.monitor_cfg: # None → 整段 monitor lifecycle 跳过
mon_lc.on_setup_done(...)
baseline

不传 = 什么都不接

两个 flag 的 default=None。不传时 args.dump_cfg / args.monitor_cfg 都是 None,训练脚本里的 if args.xxx_cfg: guard 全为 False → PrecisionDebugger / TrainerMonitorV2 根本不构造,训练循环里所有 hook 调用都被跳过。

这正是「接入零成本」的体现:接了 dcu_probe 的脚本,不传 flag 时和原生训练完全一样。按铁律,先跑这个确认 baseline 训练健康,再开采集。

②dump —— --dump-cfg 启 dump lifecycle采每 module 前向的 L0 统计
if args.dump_cfg:
dump_lc.on_train_start(
dump_cfg_path=args.dump_cfg,
seed=args.seed,
loss_output_dir=loss_output_dir,
)
# —— 训练循环内 ——
if args.dump_cfg:
dump_lc.on_step_start(model=model) # forward 前
...
dump_lc.on_step_end(step=step, loss_dict={"loss": loss_val}, grad_norm=gn_val)
dump

cfg 决定粒度 / 采哪几步 / 落哪

传 --dump-cfg 后,on_train_start 读 dump_config_resnet_L0.json 构造 PrecisionDebugger,on_step_start(model=model) 在 forward 前挂钩子,on_step_end 触发该步落盘。

cfg 里 task=statistics(采统计量,不逐元素)、level=L0(module 级,每个 nn.Module 的 forward 输入输出统计)、step=[0,1,2](只采前 3 步)。改 level=L1 就切到 API 级(逐 torch 算子),cfg 一处字段的事,脚本不用动。

③monitor —— --monitor-cfg 启三通道监控采 weight_grad / optimizer / param
if args.monitor_cfg:
mon_lc.on_setup_done(
models=model,
optimizer=optimizer, # Adam,采 mv_distribution 靠它
monitor_cfg_path=args.monitor_cfg,
grad_acc_steps=1,
loss_output_dir=loss_output_dir,
)
# —— 训练循环内,每步 optimizer.step() 之后 ——
if args.monitor_cfg:
mon_lc.on_step_end(step=step, loss_dict={"loss": loss_val}, grad_norm=gn_val)
monitor

三通道,手动 step 驱动

传 --monitor-cfg 后,on_setup_done 拿 models + optimizer 构造 TrainerMonitorV2;循环里每步 on_step_end 采一次三通道量:weight_grad(权重梯度)/ optimizer(Adam 的 exp_avg·exp_avg_sq 分布)/ param(参数本身),每通道 ops=[min,max,mean,norm,nans]。

cfg 必设 patch_optimizer_step=false —— 由循环里手动调的 on_step_end 驱动步进,不让 monitor 去 monkey-patch optimizer.step;且不开 monitors.module 通道(易抓到 wrapper 层)。

④both —— 两个 flag 都给dump + monitor 并存,LossTracker 单例去重
loss_output_dir = resolve_loss_output_dir(
dump_cfg_path=args.dump_cfg,
monitor_cfg_path=args.monitor_cfg,
)
if args.dump_cfg: dump_lc.on_train_start(...)
if args.monitor_cfg: mon_lc.on_setup_done(...)
# —— 收尾:monitor 先停 → dump 后停 ——
if args.monitor_cfg: mon_lc.on_train_end()
if args.dump_cfg: dump_lc.on_train_end()
both

两套并存,共用一份 loss_log

两个 flag 都传 → dump 与 monitor 在同一进程并存,互不冲突(dump 挂 module forward 钩子、monitor 每步采三通道量,是两套独立 API)。

resolve_loss_output_dir() 让两套共用一个 LossTracker(单例),loss_log.csv 只写一份、不会两套各写一遍。收尾按 monitor 先停 → dump 后停 的顺序调 on_train_end();LossTracker 在两者的 on_train_end 内自动 close。

采集内容由两个 cfg 文件定义

flag 只负责「传不传」;采什么、采哪几步、落哪全写在 JSON cfg 里 —— 想调粒度 / 步数,改 cfg 不动脚本。

dumpdump_config_resnet_L0.json给 --dump-cfg 用
{
"task": "statistics", # 采统计量,不逐元素落盘
"dump_path": "./resnet_dump_L0",
"rank": [], # 空 = 所有 rank(单卡就 rank_0)
"step": [0, 1, 2], # 只采前 3 步
"level": "L0", # module 级;改 "L1" = API 级
"statistics": { "summary_mode": "statistics", "scope": [] }
}
dump cfg

三个可调字段

level 决定粒度:L0 = 每个 nn.Module 的 forward 统计(生产推荐,不爆盘);L1 = 逐 torch API 算子,更细。

step 决定采哪几步(采样窗口,别全程采);dump_path 决定落哪(相对进程 cwd)。task=statistics 只落 min/max/mean/norm 等统计,不逐元素 → 体积小。

monitormonitor_v2_config_resnet.json给 --monitor-cfg 用
{
"framework": "pytorch",
"output_dir": "./resnet_monitor_v2",
"format": "csv",
"patch_optimizer_step": false, # 由手动 on_step_end 驱动
"monitors": {
"weight_grad": { "enabled": true, "ops": ["min","max","mean","norm","nans"] },
"optimizer": { "enabled": true, "mv_distribution": true, "ops": [...] },
"param": { "enabled": true, "ops": [...] }
} # 注意:不开 monitors.module 通道
}
monitor cfg

三通道 + 两条约束

三通道:weight_grad(梯度)、optimizer(开 mv_distribution 采 Adam 的 exp_avg·exp_avg_sq)、param(参数)。每通道 ops=[min,max,mean,norm,nans],format=csv 每通道一份 csv。

两条约束照搬所有框架:① patch_optimizer_step=false(手动 on_step_end 驱动 step);② 不开 monitors.module 通道(module 级监控易抓到 wrapper,与 dump 的 L0 职责重叠)。

产物结构(both 模式,ResNet50 单卡)

resnet_dump_L0/ # ← dump_path,--dump-cfg 才有 step0/dump.json # L0 每 module forward 统计(step 0/1/2 各一份) step1/dump.json step2/dump.json resnet_monitor_v2/ # ← output_dir,--monitor-cfg 才有 rank_0/ weight_grad_*.csv # 三通道各一份 csv,逐 step 追加 optimizer_*.csv param_*.csv loss_log.csv # LossTracker,dump/monitor 共用一份(both 不重复写)

验证纪律:产物由容器 root 建,权限 0o750,host 读不到要容器内 chmod -R 755 或 docker exec cat。「loss 正常打印」≠「采集成功」 —— 必须看 dump.json 有 module、csv 有真实数值行,才算这一模式真跑通。

采集控制面对照:pytorch vs dcu_megatron vs verl

同样是「开采集」,三框架的控制面复杂度差很多 —— pytorch 最直接:

框架怎么开采集启动链路命名转换是否动源码
原生 PyTorch你脚本自己的 argparse 两个 flag --dump-cfg / --monitor-cfg无 —— 直接 args.dump_cfg 拿到,零启动胶水无(flag 名你自定)无源码 patch,直接调 lifecycle hook
dcu_megatron--dcu-probe-dump L0 / --dcu-probe-monitor 双 flag穿 run.sh → pretrain → arguments 多层启动脚本要「下划线↔连字符」转换Feature 机制 monkey-patch(不改脚本本体)
verl(FSDP/Megatron 后端)manage 脚本 --dcu-probe <mode> → env → ray runtime envmanage → ray worker 透传 env—改 verl 源码插钩子(训推一致场景)
一句话记住 pytorch 的采集控制:
两个 argparse flag = 全部开关(传谁启谁,都不传=baseline) --dump-cfg → 读 dump JSON → PrecisionDebugger → step{0,1,2}/dump.json --monitor-cfg → 读 monitor JSON → TrainerMonitorV2 → 三通道 csv 采什么/采哪步/落哪 全在 JSON cfg 里,改 cfg 不动脚本;全程单侧、无 pt_compare、非训推一致
