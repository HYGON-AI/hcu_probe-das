hcu_megatron 接入 hcu_probe —— 6 坑 + 验证三件套 + L0/L1 覆盖

这里说的是独立 hcu_megatron 框架(Megatron-LM + 海光 adaptor,预训练 llama2-7B / TP1·PP2·8 卡·bf16),不是 verl 的 Megatron 后端(RL 训推一致)。

接入靠 Feature 机制、0 行改训练脚本(不是 verl 那种改 forward 源码 patch);验证是 精度对比 / 零侵入(5 模式 loss 字字一致 + dump 供离线分析),没有 pt_compare / 训推 compare 那一套。本页收敛真正会绊倒人的 6 个坑、验证三件套、以及 L0/L1 该选哪个。

先记住与 verl 的本质区别(它决定了本页的坑长什么样):
接入 verl = 改源码 patch 插钩子 vs hcu_megatron = Feature 织入,0 行改训练脚本(加 --hcu-probe-config flag 即激活) 验证 verl = 训推一致(pt_compare 逐层比) vs hcu_megatron = 精度对比 / 零侵入(dump 训练侧统计量 + 5 模式 loss 一致证零侵入,无 pt_compare)

所以本页没有"两侧配对/过滤/单调对齐"那类 compare 坑;取而代之的是 Feature 织入 + dump/monitor 生命周期 特有的 6 个坑,和一套"看 marker 判真启动"的验证纪律。

六个坑(每个一张卡:左 问题代码/配置 · 右 说明)

按"最容易误判"排序:坑 1 会让你误以为 dump 成功了其实是空的,是最迷惑的一个。

坑 1tensorboard 隐性依赖 → 静默假启动(最迷惑)"训练 loss 正常" ≠ "dump 成功了"
# hcu_probe 的 "pytorch 通用集成路径"
# (monitor v2 全部 + 通用 hcu_probe.dump)
import tensorboard # ← 缺它 = No module named 'tensorboard'
# 后果:PrecisionDebugger / monitor init 静默失败
# → 只落 loss_tracking,没有 dump.json / csv
# 但训练 lm loss 照常打印 → 看起来"成功了"(假象!)
# ⚠️ megatron L0 dump 路径不 import tensorboard
# → 会出现 "L0 dump 成功 但 monitor 失败" 的迷惑组合
最迷惑

缺库不报致命错,只静默降级

monitor v2 与通用 hcu_probe.dump 路径 import tensorboard;容器缺它时,init 走进 try/except 被静默吞掉,不崩训练 —— 你看到 loss 正常,以为在采,实际一个 dump.json / csv 都没落。

更迷惑的是:megatron L0 dump 走另一条(megatron 集成)路径,不依赖 tensorboard。于是同一次跑可能出现"L0 dump 有产物、但 monitor 什么都没有"的组合 —— 别据此判"整体成功"。

破法:跑 monitor / 通用 dump 前先确认 tensorboard 在;容器无外网就从同 image 已装的容器 docker cp 过来。判成功只看产物,不看 loss(见下方"验证三件套")。

坑 2L1 dump 必须 patch support_wrap_ops.yaml仅 L1;whl 不含此 patch
# hcu_probe/pytorch/dump/api_dump/support_wrap_ops.yaml
functional:
...
# - gelu ← 注释掉这一行
...
# - silu ← 注释掉这一行
# 不 patch 时,L1 跑 hcu_megatron 直接崩:
# ValueError: Only support fusion of gelu and swiglu (Megatron mlp.py)
仅 L1

L1 wrap 破坏了 swiglu 的 identity 检查

Megatron mcore MLP 用 self.activation_func is F.silu 做 identity 判等来决定能否走 swiglu fusion;hcu_probe L1 把 F.silu/F.gelu wrap 成新对象后,is 判等失败 → 抛 ValueError: Only support fusion of gelu and swiglu。

解法:只注释 functional: 区那两行 gelu/silu。这俩词在文件里出现多次(还有 torch: 区、npu_*),别误注别处。

易漏:whl 不含此 patch —— 每次重装 whl / 换新容器都要重打;L0 / monitor 完全不受影响。副作用:L1 dump.json 里不会再有 Functional.silu/gelu entry(精度↔兼容的取舍)。

坑 3L1 的 distributed: 段 —— 只有 EP/MoE 才需要注释别对 llama 多注释
# support_wrap_ops.yaml 里还有一段:
distributed: # send/recv/all_reduce/all_gather/all_to_all/batch_isend_irecv ...(18 个通信算子)
...
# llama2-7B(TP1/PP2,无 EP):
# → 只注释 gelu/silu 就够,distributed 段保持原样
# 实测:注释 distributed 与否,L1 逐 iter 数值字字一致
# PP 的 batch_isend_irecv 被 wrap 也不破坏
# MoE / EP(如 mixtral 的 all_to_all):
# → 才需连 distributed 段一起注释(EP all_to_all 时序敏感)
按需

非 MoE 别过度注释

完整 L1 patch 除了 gelu/silu,还有 distributed: 段的 18 个通信算子。直觉容易"全注释了保险",但非 MoE 场景反而不该动它。

llama2-7B(TP1/PP2 无 EP)实测:注释 distributed 与否,L1 逐 iter 数值字字一致,PP 的 batch_isend_irecv 被 wrap 也不影响 → 只 gelu/silu 就够。

MoE / EP(mixtral 类):EP 的 all_to_all 对时序敏感,L1 wrap 会破坏 → 这时才连 distributed: 段一起注释。

坑 4risk_level 必须大写、且只 L1 生效小写 = init failed

"task": "statistics",

# "risk_level": "all" ✘ 小写 → init failed

仅 L1

大小写敏感的枚举字段

risk_level(若用)必须是大写枚举 ALL / FOCUS / CORE;写成小写 all 会直接 init failed,而不是给个友好提示。

而且它只在 L1 cfg 生效 —— L0 下即便写了也被静默忽略,别指望它在 L0 起过滤作用。

坑 5monitor cfg 必设 patch_optimizer_step: falseMegatron 是嵌套 optimizer
{
"framework": "pytorch",
"output_dir": "./hcu_probe_dump/monitor_v2",
"format": "csv",
"patch_optimizer_step": false, # ← 必须 false
"monitors": { ... }
}
# monitor_wrapper 在 train_step 出口手动驱动:
monitor.on_step_end(result, get_args()) # 手动推进 step()
monitor

upstream 自动 patch 会扑空

upstream monitor 默认想自动 patch optimizer.step来钩每步。但 Megatron 用的是嵌套 optimizer:DistributedOptimizer → ChainedOptimizer,自动 patch 挂不到真正被调的那层 → 钩子扑空、采不到梯度/优化器态。

所以 cfg 必须 patch_optimizer_step: false,改由 monitor_wrapper 在 train_step() 出口的 on_step_end 手动驱动 step —— 这也是"薄壳 wrapper 存在的意义"之一。

坑 6monitor 不开 monitors.module 通道与 PP 的输出释放冲突
"monitors": {
"weight_grad": { "enabled": true, ... },
"optimizer": { "enabled": true, ... },
"param": { "enabled": true, ... }
# "module": { "enabled": true } ✘ 别开这个通道
}
# module 通道会 hook forward 输出,而 Megatron pipeline
# 会 deallocate_pipeline_outputs 提前释放这些张量 → 冲突
monitor

只开三通道,不碰 module

monitor v2 三通道 weight_grad / optimizer / param 采的是权重梯度、优化器动量、参数分布,与前向输出无关,安全。

但 module 通道要 hook forward 输出张量,而 Megatron pipeline 为省显存会 deallocate_pipeline_outputs 提前释放这些中间输出 → 两者冲突(读到已释放张量 / 报错)。所以 hcu_megatron 的 monitor 只开前三通道。

另一个 L1 专属自动行为(不算独立坑,但要知道):
L1 cfg 启动时,launcher 自动 export TORCHDYNAMO_DISABLE=1 → 因为 L1 的 monkey-patch(wrap 每个 API)会与 torch dynamo 图捕获冲突

L0 / monitor 不需要这一步。这也是 L1 "更细但更娇气"的一部分代价(见文末 L0/L1 覆盖表)。

验证三件套 —— 前 / 中 / 后

核心纪律一句话:必须看到 initialized / started 才算真启动;只看到 [hcu_probe-wrapper] wrapper applied 是假象(那只是装饰器挂上了,业务不一定起来 —— 见坑 1)。

三阶段 checklist(数据流)：
① 训练前 清残留 dump/ckpt · monitor 确认 tensorboard 在(坑1) · L1 确认 yaml 已 patch(坑2) → ② 训练中 grep log 看 marker,认 initialized/started → ③ 训练后 产物存在 + 数量对 + 内容合理 · chmod -R 755 让 host 可读(0o750)

★ 训练中 grep log:哪几行才算"真启动"

跑起来后 grep 训练日志,分清"装饰器已挂"和"业务真起来"两类 marker：

# —— 这两行只是"装饰器已挂",不代表在采(假象,坑 1 就卡在这)—— [hcu_probe-wrapper] train() wrapper applied via Feature mechanism [hcu_probe-wrapper] train_step() wrapper applied via Feature mechanism # —— ★ 看到下面带 initialized / started 才算真启动 —— [hcu_probe.dump] PrecisionDebugger initialized with <cfg> ← dump 真起 [hcu_probe.monitor] TrainerMonitorV2 initialized and started ← monitor 真起 # —— 收尾干净 —— msprobe ends successfully / [hcu_probe.* stopped]
  • 只有灰色两行(wrapper applied)、没有绿色两行 → 业务没真启动,大概率是坑 1(缺 tensorboard 静默失败)。
  • 看到绿色 initialized / started → dump / monitor 真的在采,产物才会有内容。
  • 结束看到 msprobe ends successfully → 生命周期收尾干净(on_train_end 正常触发)。
③ 训练后:验产物(别凭"文件存在"就判过)
存在 → 数量对(dump step0/1/2 各 rank 的 dump.json;monitor csv = 8 rank × 三通道) → 内容合理(dump 看 module 数 / shape / Max·Min·Mean·Norm,查 NaN/Inf;csv 看各层 min/max/mean/norm/nans 有真实数值)

产物默认 0o750(容器 root 建的),host 读不了 → 容器内 chmod -R 755 <dump目录> 或 docker exec cat。零侵入的判据:mode1 baseline 与 mode2 L0 / mode4 monitor 的 lm loss、grad norm 字字一致(实测 lm loss 9.087223 / grad 4.535,nan 0);L1 因 wrap 微扰略偏(9.087196),属预期。

L0 vs L1 覆盖差异 —— 生产选 L0,深挖用 L1

两个 level 不是"越细越好"。L0 零依赖零 patch = 生产推荐;L1 更细但要 patch + 关 dynamo,而且 TE 融合算子它也抓不到。

维度L0(module 级)L1(API 级)
采集粒度每个 module 的 forward 统计量(Max/Min/Mean/Norm)Functional / Tensor / Torch API 算子级,更细
定位能力定位"哪一层 / 哪个 module 不一致"定位"哪个算子 / 哪个 API 调用"
需 yaml patch(gelu/silu)❌ 不需✅ 需(坑 2;MoE 还要 distributed 段,坑 3)
需 TORCHDYNAMO_DISABLE❌ 不需✅ 需(L1 monkey-patch 与 dynamo 冲突)
依赖 tensorboard❌ 不(走 megatron 集成路径)dump 本身不;monitor 通道才依赖(坑 1)
TE 融合算子可见性module 边界可见输入/输出统计⚠️ 抓不到 —— 计算在 TE(TransformerEngine)kernel 内,不经 Python 层 API
对训练的微扰零(与 baseline loss 字字一致 9.087223)极小(wrap 微扰,9.087196)
适用✅ 生产推荐:常态化精度巡检 / 快速定位哪层算子级精度剖析 / 深挖单层内部
一句话选型:
L0 = 零 patch·零依赖·零微扰·定位到层 → 日常首选 L1 = 要 patch yaml + 关 dynamo,细到算子,但 TE kernel 内的融合算子照样看不见 → 只在需要算子级证据时才上
