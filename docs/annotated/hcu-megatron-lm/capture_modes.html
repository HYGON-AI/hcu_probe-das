hcu_megatron 5 采集模式 + CLI flag 三层链路 —— hcu_probe dump / monitor

这里说的是独立 hcu_megatron 框架(Megatron-LM + 海光 adaptor,预训练 llama2-7B)—— 不是 verl 的 Megatron 后端(RL 训推一致),别混。

hcu_probe 在 hcu_megatron 里做的是 单侧精度采集 + 零侵入验证:采训练侧统计量供离线精度分析,并用「5 模式 loss 字字一致」证明钩子零侵入。没有 pt_compare、没有训推双侧比对 —— 这是它和 verl 最本质的区别。

★ 核心能力:hcu_probe 的采集 API(PrecisionDebugger dump + TrainerMonitorV2 monitor)

hcu_probe 在 hcu_megatron 里发挥什么效果

和 verl 的 pt_compare(双侧逐算子比对)不同,hcu_megatron 用的是 hcu_probe 的采集能力 —— 两套独立子系统,经 Feature 钩子织进 megatron 的 train_step:

# dump:每个 train_step 前向前后开关采集器,落逐 module / 逐 API 统计量 PrecisionDebugger(config_path) # task=statistics, level=L0/L1, 只 Max/Min/Mean/Norm ├ on_step_start → debugger.start(model) # 前向前 └ on_step_end → debugger.stop() + step() # 前向后 # monitor:另一套 API,采训练态三通道 → csv(不碰 dump) TrainerMonitorV2(monitor_config) # weight_grad / optimizer / param

它产出什么(效果):

  • dump(PrecisionDebugger)→ 每个 module(L0)或每个 API 算子(L1)的 dump.json 统计量,供离线精度分析(定位"哪层/哪算子数值异常")。
  • monitor(TrainerMonitorV2)→ 逐 step 的梯度 / 优化器 / 参数三通道 csv,做训练态监控(看梯度爆炸 / NaN / 参数漂移)。
  • 零侵入证明:开采集与 baseline 的 lm loss 逐 iter 字字一致(L0/monitor/combined = 9.087223)→ 说明钩子没改变训练数值。

关键区别:这里不做训推一致、不调 pt_compare —— hcu_megatron 是纯训练框架,采集的是单侧训练态数据。verl 那套「训练 dump ↔ 推理 dump 逐算子比误差」在这里根本不存在。

CLI flag 三层链路(下划线 flag 怎么一路变成 megatron 认的连字符 flag):
① launcher 解析 --hcu_probe_config(下划线,=号) → ② train 脚本 读 level(L1 自动 TORCHDYNAMO_DISABLE)+ 组装 HCU_PROBE_ARGS(下划线转连字符) → ③ pretrain_gpt.py argparse 收 --hcu-probe-config(连字符,Feature register_args 注册的)

一、CLI flag 三层链路(核心坑 = 下划线 ↔ 连字符)

megatron 的 pretrain_gpt.py 只认连字符 --hcu-probe-config;而 launcher 惯用下划线 --hcu_probe_config。启动脚本必须做「下划线 → 连字符」转换,否则 flag 被静默吞掉、行为退回 baseline(无报错、最难查)。

①launcher 层 —— 解析下划线 flag加进脚本已有的入参循环
# hcu_megatron 的 train 脚本本就有 `for para in $*` 的 if/elif 链
# 解析 --data_path 等,照同样写法多加 3 个分支:
elif [[ $para == --hcu_probe_config* ]]; then hcu_probe_config=${para#*=}
elif [[ $para == --hcu_probe_seed* ]]; then hcu_probe_seed=${para#*=}
elif [[ $para == --hcu_probe_monitor_config* ]];then hcu_probe_monitor_config=${para#*=}
接收

用下划线接命令行

用户跑 bash launcher.sh --hcu_probe_config=...L0.json,launcher 用下划线形式接住(shell 里带连字符的变量名不合法,所以约定俗成用下划线)。

两层脚本要穿两层:若结构是「外层 run_*.sh + 内层 train_*.sh」,外层要把 --hcu_probe_config=$xxx 透传给内层,内层才收得到;否则外层静默忽略。

②★train 脚本 —— L1 自动关 dynamo + 下划线转连字符整条链路的灵魂
# (b) L1 自动关 dynamo(读 cfg 的 level 判断,不用用户手动)
if [[ -n "${hcu_probe_config}" && -f "${hcu_probe_config}" ]]; then
level=$(python3 -c "import json;print(json.load(open('${hcu_probe_config}'))['level'])")
[[ "${level}" == "L1" ]] && export TORCHDYNAMO_DISABLE=1
fi
# (c) 下划线 flag → megatron 连字符 flag,拼成参数数组
HCU_PROBE_ARGS=()
[[ -n "${hcu_probe_config}" ]] && HCU_PROBE_ARGS+=(--hcu-probe-config "${hcu_probe_config}")
[[ -n "${hcu_probe_seed}" ]] && HCU_PROBE_ARGS+=(--hcu-probe-seed "${hcu_probe_seed}")
[[ -n "${hcu_probe_monitor_config}" ]] && HCU_PROBE_ARGS+=(--hcu-probe-monitor-config "${hcu_probe_monitor_config}")
核心坑

下划线 → 连字符,少这一步全盘失效

HCU_PROBE_ARGS+=(--hcu-connective...) 这三行把下划线变量拼成 megatron argparse 认的连字符 flag。忘了转 → megatron 收不到 → 静默走 baseline、无任何报错。

L1 自动 TORCHDYNAMO_DISABLE=1:脚本读 cfg 里的 level,是 L1 就自动关 dynamo(L1 的 API 级 monkey-patch 与 torch dynamo 图捕获冲突)。用户不用手动 export。

③pretrain_gpt.py —— megatron argparse 收连字符 flagFeature 的 register_args 注册的那个 flag
# HcuProbeFeature.register_args() 里注册的(见接入机制页):
group.add_argument('--hcu-probe-config', type=str, default=None,
help='Path to hcu_probe config JSON ...')
# train 脚本把 ${HCU_PROBE_ARGS[@]} 拼进 APP,与其他 *_ARGS 并列:
APP="python -u ${MEGATRON_PATH}/pretrain_gpt.py \
${GPT_MODEL_ARGS[@]} ${TRAINING_ARGS[@]} ... \
${HCU_PROBE_ARGS[@]}" # ← 加这一行即接通
收 flag

megatron 端只认连字符

--hcu-probe-config 是 Feature 的 register_args() 用 add_argument 注册进 megatron argparse 的。所以 ② 必须先把下划线转成它,argparse 才 match 得上。

把 ${HCU_PROBE_ARGS[@]} 拼进组装 pretrain_gpt.py 的 APP 字符串就接通了 —— 训练脚本本体只加这一行,megatron 源码 0 改动。收到 flag 后,启动时 Feature 的 register_patches() 把 dump wrapper monkey-patch 进 train_step。

二、dump / monitor 采集器 lifecycle

flag 接通后,采集器的真正开关由钩子 wrapper 驱动 —— 薄壳只透传,业务全在 whl 的 hcu_probe.integrations.megatron.dump / .monitor 翻译层。

④dump lifecycle —— on_step_start / on_step_end 经 hook 织入PrecisionDebugger 的开关点
# hcu_probe_wrapper.py:train_step 薄壳(verbatim)
def wrapped_train_step(forward_step_func, data_iterator, model, *args, **kwargs):
dump.on_step_start(model, get_args()) # 前向前 debugger.start(model)
result = original_train_step(forward_step_func, data_iterator, model, *args, **kwargs)
dump.on_step_end(result, get_args()) # 前向后 debugger.stop() + step()
return result
# train() 薄壳:on_train_start 起 PrecisionDebugger、finally on_train_end 收尾
dump.on_train_start(get_args()) # PrecisionDebugger(config_path) initialized
lifecycle

包住每个 train_step 的前向

on_step_start 在真实 train_step 前 start(model)、on_step_end 在其后 stop()+step() —— 采集窗口正好罩住一个 step 的前向(和反向,取决于钩子内 grad 上下文)。

cfg 关键字段:task=statistics(只统计 Max/Min/Mean/Norm)、level=L0/L1、step:[0,1,2](只采前 3 步)、dump_path。真启动看 log PrecisionDebugger initialized,别只看 wrapper applied 的 marker(见坑与验证页)。

⑤★L1 yaml patch —— 注释 support_wrap_ops.yaml 的 gelu / silu仅 L1 需要,whl 不含
# hcu_probe 包内 pytorch/dump/api_dump/support_wrap_ops.yaml
functional: # ← 只改这个 functional 区(文件靠前)
- conv2d
- linear
...
# - gelu ← 注释掉这一行
# - silu ← 注释掉这一行
tensor: # ← torch/tensor/npu/distributed 区的 gelu/silu 别动
仅 L1

不注释就崩在 swiglu fusion 检查

L1 会 wrap F.gelu/F.silu,让 Megatron MLP 的 activation_func is F.silu identity 检查失败 → ValueError: Only support fusion of gelu and swiglu。注释掉 functional: 区这两行即解。

只注 functional 区:这两个词在文件里出现多次(torch 区、npu_* 区、distributed 区都有),误注别处会破坏其它算子采集。非 MoE(llama TP1/PP2)只此够;MoE/EP 因 all_to_all 时序敏感,才要连 distributed: 段一起注释。L0/monitor 完全不需要 patch。

采什么:什么都不采

baseline 的作用是提供零侵入判据:后面开采集的 loss 要拿它逐 iter 对齐。铁律 —— 先跑通健康 baseline 再接 hcu_probe,否则在坏训练上验采集毫无意义。

mode2L0 dump —— module 级(生产推荐)不依赖 tensorboard、不需 yaml patch
bash <launcher>.sh --hcu_probe_config=$(realpath L0.json)
# cfg: "task":"statistics", "level":"L0", "step":[0,1,2]
L0

采什么:每 module forward 的统计量

抓每个 module 前向输入/输出的 Max/Min/Mean/Norm,定位"哪一层数值异常"。粒度粗但快、稳、不爆盘,不依赖 tensorboard、不需改 yaml → 生产首选。loss 与 baseline 字字一致。

bash <launcher>.sh --hcu_probe_config=$(realpath L1.json)
# 同 L0,仅 "level":"L1";launcher 自动 export TORCHDYNAMO_DISABLE=1
L1

采什么:Functional / Tensor / Torch 算子

细到每个 API 算子。代价:需 ⑤ yaml patch + 自动关 dynamo;且 loss 有微扰(9.087223→9.087196,API 级 wrap 织入所致)。Megatron 用 TE 融合算子时部分计算在 kernel 内,L1 也抓不到 Python 层 API。

采什么:梯度 / 优化器 / 参数

TrainerMonitorV2 逐 step 采三通道(weight_grad / optimizer / param)的 min/max/mean/norm/nans,落 csv(8 rank × 15 列),看梯度爆炸 / NaN / 参数漂移。不开 module 通道(与 pipeline deallocate_pipeline_outputs 冲突)、patch_optimizer_step:false(见坑页)。

mode5combined —— L0 dump + monitor 同开两钩子并存无冲突

combined

采什么:dump + csv 叠加

L0 dump(钩 train_step 前向)与 monitor(钩 train_step 出口采训练态)两钩子并存、互不干扰,dump.json 与 csv 同时落盘。LossTracker 单例去重避免两套采集重复记 loss。loss 仍字字一致 = 双钩子也零侵入。
