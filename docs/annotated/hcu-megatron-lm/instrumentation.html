hcu_probe × hcu_megatron（独立框架）—— 接入机制标注（Feature 织入，0 行改训练脚本）

hcu_megatron = Megatron-LM 子模块 + 海光 adaptor 的预训练框架（本例 llama2-7B，TP1/PP2，8 卡 bf16）。接入 hcu_probe 不改一行训练脚本、不改一行 megatron 源码——靠 adaptor 自带的 Feature 机制：写 4 个几十行薄壳、登记进 ADAPTOR_FEATURES list，启动时用 patch_manager monkey-patch 把 dump / monitor 的生命周期钩子织进 megatron 的 train / train_step / setup_model_and_optimizer。

本页标注这 4 个薄壳分别是什么、怎么登记、5 个 hook 点各挂在 megatron 哪个函数。左侧是薄壳的 verbatim 源码（绿色高亮 = 你新增的文件 / 行），右侧是说明。与 verl 的本质区别：verl 训推一致是在 verl / vllm 源码里逐处插 patch；hcu_megatron 是零侵入 Feature 织入，训练命令加一个 --hcu-probe-config flag 即激活，不加就是原生 megatron 行为。

核心机制
ADAPTOR_FEATURES 显式登记 + register_patches monkey-patch 织入——hcu_megatron 的 features_manager 维护一个 ADAPTOR_FEATURES list（features_manager/__init__.py），没有自动扫描，Feature 靠这个 list 显式登记。启动时框架遍历它、调每个 Feature 的 register_patches(patch_manager, args) → patch_manager.register_patch('megatron.training.training.train', wrapper, apply_wrapper=True) 把 wrapper monkey-patch 织进 megatron 的 train / train_step / setup_model_and_optimizer。
所以接入 = 拷 4 薄壳进 adaptor/features_manager/probe/ + 在 list 加 2 行 import + 2 个实例（HcuProbeFeature() / MonitorFeature()）+ 训练命令加 flag。megatron 本体、pretrain_gpt.py、run_*.sh 0 改动。薄壳只有几十行（注册 flag + 注册 patch + 透传），业务逻辑全在 whl 翻译层 hcu_probe.integrations.megatron.*。

总览：接入面 = 5 个文件（4 薄壳 + 1 处登记），全在 adaptor 内

接入不跨仓、不改 megatron：4 个薄壳是新建文件放进 hcu_megatron/adaptor/features_manager/probe/，唯一改到的既有文件是 features_manager/__init__.py（加 2 import + 2 实例登记）。业务逻辑全在已安装的 hcu_probe whl。

与 verl 的本质区别 —— 改源码 patch vs Feature 织入
verl（训推一致）：在 verl / das vllm 的 forward 路径上逐处插 patch（dp_actor 钩 compute_log_prob、vllm gpu_model_runner 钩 execute_model…），跨 3 个 git 仓改真实源码，目标是训练侧 vs 推理侧逐层 pt_compare 比数值。
↕
hcu_megatron（精度对比 / 零侵入）：0 行改训练脚本、0 行改 megatron 源码——4 个薄壳 + ADAPTOR_FEATURES 登记 + 一个 CLI flag。只 dump 训练侧统计量供离线精度分析，并用 5 模式 loss 字字一致证「接了 hcu_probe 不扰动训练」。没有推理侧、没有 pt_compare、没有训推 compare 那一套。

薄壳把 megatron 生命周期翻成 4 个 hook（三件套在翻译层）

薄壳只透传 4 个 hook 调用，真正的 hcu_probe 三件套（PrecisionDebugger(config_path) → forward 前 start(model) → forward → stop() + step()）藏在 whl 翻译层 hcu_probe.integrations.megatron.dump 里，薄壳看不到：
train() 入口 on_train_start（建 debugger）→ 每个 train_step() 入口 on_step_start(model)（start）→ 前向 + 反向（hcu_megatron 钩的是含 loss.backward() 的完整 train_step，故前向 + 反向都采，区别于 verl 只 no_grad 前向）→ train_step() 出口 on_step_end（stop + step）→ train() finally on_train_end。
cfg 关键字段：task=statistics（只 Max/Min/Mean/Norm，免爆盘）、level=L0（module 级）/ L1（API 级）、dump_path。产物 = 每 step 一份 dump.json（模式细节见采集模式页）。

A 登记

光拷文件不登记 = 静默无效

hcu_megatron 没有自动扫描，Feature 全靠 ADAPTOR_FEATURES list 显式登记。把 4 个薄壳拷进 probe/ 子目录后，还必须在这里加 2 行 import + 2 个实例。漏了这步 → 训练照跑、无报错、行为与 baseline 完全一样（dump / monitor 静默失效）。

+ patch_manager.register_patch(
+ 'megatron.training.training.train_step', # 织进 megatron train_step()

register_args 定 flag，register_patches 定挂点

register_args 给 megatron argparse 注册 --hcu-probe-config（dump cfg 路径）和 --hcu-probe-seed。传了 flag 才有 dump，不传 = 原生 megatron。

register_patches 是织入核心：patch_manager.register_patch('megatron.training.training.train', wrapper, apply_wrapper=True) 把 wrapper monkey-patch 到 megatron 的 train 和 train_step。apply_wrapper=True = 把 wrapper 当装饰器套在原函数外（而非替换），所以原逻辑一行不动。

AbstractFeature / patch_manager 都是 hcu_megatron 自带的，薄壳只继承、不实现。

D 翻译层

只透传 lifecycle，业务全在 whl

2 个 wrapper 一共十几行：train 外面包 dump.on_train_start / on_train_end，train_step 外面包 dump.on_step_start(model) / on_step_end(result)。没有一行 hcu_probe 业务逻辑——PrecisionDebugger 的 init / start / stop / step、rank 过滤、cfg 解析全在 whl 的 hcu_probe.integrations.megatron.dump。

薄壳只认 megatron 的函数签名（forward_step_func, data_iterator, model, ...）并原样转发，框架换版本也很少动。on_step_start 拿到 model 是为了 PrecisionDebugger.start(model) 注册前向 / 反向 hook。

marker [hcu_probe-wrapper] ... wrapper applied via Feature mechanism 只表示「装饰器已挂」；真启动要看翻译层打的 PrecisionDebugger initialized（见验证页）——别把「已挂」当「已采」。

B 织入
旁支 · 训练监控

monitor 比 dump 多挂一个 setup

monitor 要拿到 model + optimizer 才能看 weight_grad / optimizer / param 三通道，所以比 dump 多挂一个 setup_model_and_optimizer——它的出口正好返回 model 和 optimizer。

flag 是独立的 --hcu-probe-monitor-config，与 dump 的 --hcu-probe-config 互不影响、可同开（采集模式页 mode5 combined）。

monitor 是训练健康监控，不属于「精度对比」主线，列在这里作对照。它和 dump 一样零侵入。

+ def monitor_setup_model_and_optimizer_wrapper(original_func):

+ monitor.on_train_end()
+ return wrapped_train

setup 出口起 monitor，step 出口驱动

setup_... wrapper 用 @wraps 保签名，在原函数返回 (models, optimizer, scheduler) 后调 monitor.on_setup_done(models, optimizer, args) 起 TrainerMonitorV2；train_step 出口调 monitor.on_step_end；train 的 finally 调 on_train_end。业务在 hcu_probe.integrations.megatron.monitor。

★ Megatron 是 nested optimizer（DistributedOptimizer → ChainedOptimizer），upstream 自动 patch optimizer_step 会扑空 → cfg 必须 patch_optimizer_step: false，由 wrapper 在 on_step_end 手动驱动 step()（见验证页坑 5）。

5 个 hook 点 → whl 翻译层

薄壳一共只暴露这几个 hook；每个 hook 挂在 megatron 哪个函数、什么条件触发如下。翻译层 = hcu_probe.integrations.megatron.{dump,monitor}，真正的采集逻辑在那里。

为什么薄壳能这么薄 —— 业务逻辑（PrecisionDebugger init / TrainerMonitorV2 启停 / rank 过滤 / cfg 解析）全在 hcu_probe whl 的 hcu_probe.integrations.megatron.* 翻译层，薄壳只做「注册 flag + 注册 patch + 透传 hook」。所以 trl / deepspeed / lightning 等框架接入也只需类似的几行薄壳——换框架换的是薄壳挂点，不动翻译层。要加新 hook 点（如在 pretrain_gpt.forward_step 也 dump），在对应 register_patches() 多注册一条 + 写对应 wrapper 薄壳调 dump.on_xxx 即可。
