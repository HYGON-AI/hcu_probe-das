run_megatron_compare.py 代码逻辑 —— 用 dcu_probe 的 pt_compare(backend=megatron) 复核 verl 0.7 Megatron 训推一致性

这个脚本本身不算精度 —— 它做的是「把训练侧(mcore/TE)、推理侧(das vllm)的 dump 配对好、挑对样本,再交给 dcu_probe 的官方比对工具 pt_compare 去逐算子算误差」。

真正发挥效果的 dcu_probe 工具 = pt_compare;脚本的 4 步里,前 2 步都是在「为 pt_compare 准备能对齐的输入」,第 3 步才调 pt_compare,第 4 步读它的结果。比 FSDP 0.7 少一步 —— megatron 的推理侧是 das vllm 0.11,模块序干净,不需要 FSDP 0.7 那道 72 个交错模块的过滤。

★ 核心工具:dcu_probe 的 pt_compare(官方精度比对 API,backend=megatron)

pt_compare 是什么、发挥什么效果

来自 dcu_probe.pytorch.compare.pt_compare(= 华为 msprobe compare 的 DCU fork)。它是 dcu_probe 提供的官方逐算子精度比对能力,本脚本调的就是它:

# 训练侧 dump(mcore/TE)↔ 推理侧 dump(das vllm),逐算子比对 pt_compare({"npu_path": 训练侧dump.json, "bench_path": 推理侧dump.json}, output_path, consistent_check=True, backend="megatron")

它内部干这几件事(效果):

  • 读两侧 dump.json → 建两张算子表(NPU=训练侧、Bench=推理侧;方向反了就 match 不上)。
  • consistent_check=True → 走 verl 训推一致专用比对算法(而非普通逐 tensor 比)。
  • backend="megatron" → 用 MEGATRON_MODULE_MAP 把 mcore/TE 命名映射到 vllm 命名(decoder.layers.N.self_attention.linear_qkv → model.layers.N.self_attn.qkv_proj 等)。
  • consistent_match → dual_monotonic_sort → 把两侧算子按位置单调对齐;张量并行(SP)切片会自动 cat 回整层再比。
  • 逐算子算 NormRelativeErr(Norm 相对误差)→ 落 compare_result_*.xlsx。

关键(megatron 比 FSDP 0.7 简单):megatron 后端推理侧用 das vllm 0.11,dump 里的模块序干净、没有训练侧缺失的交错模块 → 可以直接把配对好的两侧 dump 喂 pt_compare,dual_monotonic_sort 一次就过。而 FSDP 0.7 用 das vllm 0.18.1,推理 dump 多出 72 个交错模块会撑爆对齐,必须先过滤 —— megatron 这里没有那道坎。

配对

把两侧对上号

pt_compare 一次只比一对 dump.json(一个训练前向 vs 一个推理前向)。这步用 request_id 把两侧对上:推理侧从 dispatch_log 找、训练侧从 update_actor_log 找。

只取单 request(推理 requests==1 / 训练 num_requests==1)的 prefill —— 多 request 拼 batch 的 dump 是混合张量,无法逐层比。das 会给 id 加 -<8hex> 后缀,strip 去掉才对得齐。

megatron 特有:训练侧 request_id 是 compute_log_prob 开头从 non_tensor_batch 抢救出来的(forward_backward_batch 切 micro_batch 只 split .batch、会丢 non_tensor),再由 update_actor_log 逐样本落盘,这里才配得上。

token 数一致 = 真·同 prompt

tok() 取 embed 层输入的 token 数。megatron 两侧 embed 命名不同:训练侧是 mcore 的 word_embeddings.VocabParallelEmbedding,推理侧是 vllm 的 embed_tokens.VocabParallel —— 所以两边各用各的关键字取。

两侧 token 数相同,才说明喂进模型的是同一个 prompt 的完整 prefill(没被 prefix cache 截断、没被 batch 拼)。选一个这样的 rid,拿它的训练 dump(train[rid])和推理 dump(gen[rid])去比 —— 这就是要喂给 pt_compare 的那一对。

dcu_probe 工具

官方逐算子比对就在这两行

前 2 步全是铺垫,这两行才是真正发挥效果的 dcu_probe 工具。它读两侧 dump.json,用 consistent_check+backend=megatron 的专用算法把算子对齐(MEGATRON_MODULE_MAP 命名映射 + dual_monotonic_sort 单调对齐 + SP 切片自动 cat),逐算子算 Norm 相对误差,落 xlsx。

统计

排除结构性不可比,报叶子算子分布

pt_compare 会把所有算子都列进 xlsx,包括结构性不可比的:整层 wrapper(TransformerLayer 的输出是残差和)、IdentityOp 融合占位。这步先过滤 IdentityOp、只留带 output 的叶子算子输出统计 NormRelativeErr。

结果:真算子 output 中位 0%、266/289(92%)<1%;叶子算子(layernorm 96 / linear 96 / attention 48 / act_fn 24 / embed 1)全 <1%,embed 与 MLP down_proj RelErr = 0。剩下 23 个 >1% 全是 TransformerLayer 整层聚合输出(NPU l2≈1720 vs Bench≈54,约 32× 量级差 + shape [S,1,H] vs [S,H] 的 massive-activation,方法学排除、非真发散),与 0.8.0 megatron 吻合。

megatron 0.7 的 compare 为什么比 FSDP 0.7 少一步

关键区分:pt_compare 是 dcu_probe 的官方比对工具(底层能力),两个后端都用它;差别只在「喂进去之前要不要过滤」。决定因素 = 推理侧 das vllm 的版本。

① 为什么 megatron 能直接喂 pt_compare
megatron 后端推理走 das vllm 0.11,它的 dump 模块序和训练侧 mcore/TE 能一一单调对上 —— 没有"训练侧缺失、位置又交错"的模块。所以配对好、挑好样本后,直接 pt_compare(consistent_check=True, backend="megatron"),dual_monotonic_sort 一次就过,不崩。这和 0.8.0 megatron 是同一套(都用 das vllm 0.11)。

② 为什么 FSDP 0.7 必须多一步过滤
FSDP 0.7 推理走 das vllm 0.18.1,推理 dump 里比训练侧多出 72 个训练侧无对应、且位置交错的模块(Triton.kernel_unified_attention×24 + reshape_and_cache×24 + 独立 rotary_emb×24)。不剔它们,pt_compare 的 dual_monotonic_sort 因两侧位置无法同时单调递增而 raise Conflicting comparison data → 崩。所以 run07_filtered.py 要先把它们过滤掉(338→266)才喂 pt_compare。

③ 底层工具是同一个
两个后端用的都是同一个 pt_compare,只是 backend 参数不同(megatron 用 MEGATRON_MODULE_MAP、fsdp 用 FSDP_MODULE_MAP)。megatron 版的脚本因此更短、更直——省掉了那道过滤,把精力全放在配对与样本挑选上。

一句话记住 megatron vs FSDP 0.7 的 compare 差异:
pt_compare = dcu_probe 官方比对工具(核心能力,两后端共用) run_megatron_compare.py = 4 步·无过滤:配对 → 挑样本 → 直接喂 pt_compare(backend=megatron)→ 统计 [266/289 <1%] run07_filtered.py(FSDP 0.7)= 5 步·多一步过滤:配对 → 挑样本 → 剔 72 交错模块 → 喂 pt_compare(backend=fsdp)→ 统计 [98/98 <1%] 差异根因 = 推理侧 das vllm 版本:megatron 用 0.11(干净)、FSDP 0.7 用 0.18.1(72 交错模块)
