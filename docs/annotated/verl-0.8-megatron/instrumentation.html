hcu_probe × verl 0.8.0（Megatron 后端）—— 插桩位置标注

RL 训练里同一个模型既做推理（das vllm rollout 生成 response）又做训练（Megatron actor 的 compute_log_prob 前向）。两侧对同一 prompt 的 prefill 前向理论上数值一致。hcu_probe 在两侧分别 dump 前向统计量，按 request_id 配对、比相对误差，定界精度差在训练侧还是推理侧。

本页标注 hcu_probe 在哪几个源码文件、哪几处方法插桩（绿色高亮 = 新增行，右侧是插桩说明）。全部改动靠 env 开关门控——不开 dump 就是 verl 原行为（最小侵入）。训练侧钩子全部落在 0.8.0 的 NEW engine：MegatronEngineWithLMHead.forward_step（verl/workers/engine/megatron/transformer_impl.py），既不是 0.7.1 的 LEGACY megatron_actor.py、也不是 FSDP 的 dp_actor。

★★ 与 0.7 的核心区别 —— 0.8 钩 NEW engine 的 MegatronEngineWithLMHead.forward_step（transformer_impl.py），0.7.1 却因 NEW engine 权重未物化 bug 必须退回 LEGACY MegatronPPOActor

verl 0.8.0 收敛成统一的 Engine 抽象：actor 前向走 verl/workers/engine/megatron/transformer_impl.py 里的 MegatronEngine / MegatronEngineWithLMHead。megatron 走 PP 调度，没有 FSDP 那样显式的 micro_batch for 循环，前向由 get_forward_backward_func() 接管，所以钩子下沉到 forward_step（transformer_impl.py:1016 的 forward_fn 前后）。

与 0.7.1 恰好相反：0.7.1 的 NEW engine compute_log_prob 有权重未物化 bug——前向一进第一个 leaf word_embeddings 就 F.embedding 报 data is not allocated yet（DUMP_ON=0 零插桩也照崩 → 引擎 bug、与 hcu_probe 无关），所以 0.7.1 必须退回 LEGACY MegatronPPOActor（megatron_actor.py）并不加 use_legacy_worker_impl=disable。而 0.8.0 的 NEW engine 已修好、可直接钩。

一句话：0.8.0 就钩 NEW engine 的 forward_step；别套 0.7 的 megatron_actor.py、别套 FSDP 的 dp_actor、也别套 v0.6.x SPMD 的 fsdp_workers.update_actor——四代路径互不通用。

这是训练侧被 dump 的那一次前向。0.8.0 megatron 走 PP 调度、无显式 micro_batch 循环，真前向就是 MegatronEngineWithLMHead.forward_step 里的 forward_fn(model, input_ids, ...)（mcore 前向）。把它用 hcu_probe 三件套围起来，就抓到了训练侧 prefill 前向的逐算子统计量。

B 对齐 · 裁 response

让训练前向只算 prompt prefill

推理侧 prefill 只吃 prompt；但训练侧 compute_log_prob 默认吃 prompt+response 整条序列。两侧要比 prefill，就得把训练侧的 response 裁掉，只留 prompt。

PROMPTS_ONLY=1 时把 input_ids/attention_mask/position_ids 的尾部 response 段切掉，responses 等清空到 0 长——这样训练前向的 prefill 与推理侧对齐。

副作用：response_mask 全 False → loss 退化，破坏训练。所以 PROMPTS_ONLY 只用于 dump 采集 run，训练健康要另跑不开它的普通 run 单独验证（训推一致性与训练健康是两件正交的事）。

为什么要透传

verl 用 ray 起多进程 worker。actor 前向、vllm 推理都在 ray worker 子进程里跑，shell export 的 env 到不了 worker。

把 dump 的所有开关塞进 PPO_RAY_RUNTIME_ENV（driver import 时取值），ray 起 worker 时注入 → _ensure_debugger（训练侧）/ gpu_model_runner（推理侧）才读得到。TORCHDYNAMO_DISABLE 关编译避免影响 dump 数值；MONITOR_CONFIG 供可选的 monitor 三通道。与 FSDP 0.8 相同。

A 采集 · 推理侧（只 prefill）

只在 prefill 门控，防爆盘

推理侧被 dump 的那一次前向——挂内层 self.model(...)（with set_forward_context 块内）。

_hcu_prefill = 只在有新 request（prefill）时 dump：一个 response 要 ~上千次 execute_model（decode），全 dump 会瞬间爆盘。只抓 prefill 那次即与训练侧对齐。

★ CUDAGraphWrapper 解包：self.model 是包装器，hcu_probe 的 check_model 只认 nn.Module，要 while ... hasattr("runnable") 循环解包到真实 module 再传 debugger（prefill 走 eager 会命中，decode 走 cudagraph 不 dump，无碍）。硬前置：enforce_eager=True——compile+cudagraph 会绕过 hook 导致 dump 空。

★ 已知问题：run 跑不久（两种失败，均非 hcu_probe / 非数值）

① host-RAM OOM（崩，exit 137）：全 offload（param/optimizer/grad_offload=True）把 8B 优化器态压进 CPU → 单进程 cpu_memory_used 333GB，节点 751GB + ~40 容器共享 → OS OOM-kill（Socket closed + exit 137）。GPU 只用 17.5/64GB，offload 是有害多余开销。无 dump 的普通 run 同样崩 = dump 洗清（只是死前最后一条日志、非因果）。修法（实测）：关 optimizer_offload/grad_offload → GPU 17.5→36GB 常驻无 OOM、步速 100s→32s/it、step1-4 干净。

② vllm validation-rollout 集合通信挂死（关 offload 后仍在 step5 挂）：py-spy 实证 driver 卡 ray_trainer.py:643 _validate、vllm EngineCore 卡 shm_broadcast.acquire_read（向 8 个 TP worker 发 execute_model 等不到响应）、GPU 空转 = vllm-on-HCU rollout 集合通信挂死。触发点 = in-loop validation 的 rollout；修法：trainer.test_freq=-1 关 in-loop validation → 稳跑 step24+（GPU 在算、无崩无挂）。

长训配方（实测可用）= 关 optimizer_offload/grad_offload（解模式①）+ trainer.test_freq=-1（避模式②）。本流程只需跑出前几步 dump 即可做一致性比对，别期望长跑（早期 step 的 dump 实测有效、0 NaN）。训练健康要另跑不带 dump/PROMPTS_ONLY 的普通 run（已验 megatron 普通训练 grad_norm 有限、给够 response=1024 时 reward 前半 0.36→后半 0.64 翻倍、step39=1.0 全对，教科书式 GRPO 曲线）。

★ 诚实定界（直接读官方 compare xlsx 复核，别夸成"逐 tensor 全一致"）

训推一致 = 可比叶子算子 + 激活统计量一致，不是全部 tensor 一致。官方 pt_compare 的 4867 行实测：3927 pass（253 权重同源必同 + 3673 激活统计量一致 + 1）、939 "error" 里 903 是 requires_grad 元数据差（训练 True / 推理 False，benign）、1 是 int dtype（值相同）、35 是整层 TransformerLayer/IdentityOp。

被排除的 35 个整层输出量级显著不同（训练侧残差流 massive-activation max~2.2e4 vs 推理侧 ~5.7，shape [S,1,H] vs [S,H]）—— 这是方法学排除（不同模块边界 + LLaMA/Qwen 残差 massive-activation 现象），不是 bug，但不能据此宣称逐 tensor 全一致。
